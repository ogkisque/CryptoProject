# Отчёт об экспериментальном исследовании CPU и GPU

> **Статус: каркас (этап 7, часть А).** Выводов здесь пока нет: они пишутся в части В по присланным результатам
> запусков на GPU-машине (`docs/gpu_workflow.md`). Все числа и графики берутся из `analysis/summary.md`, который
> генерирует `bench/analysis/analyze.py`; руками числа не правятся.

## Как получены данные

```bash
CUPQC_ROOT=/путь/к/cupqc-sdk ./scripts/gpu_run_all.sh --quick     # проверка: сборка, ctest, smoke, quick.json
./scripts/gpu_run_all.sh --runs 3                                  # полный: full.json x3 + gpu_*.json
python3 bench/analysis/analyze.py bench/results/<прогон>/results_full_run*.csv --out <каталог>   # повтор анализа
```

Архив `bench/results/<время>_<хост>.tar.gz` содержит: `RUN_SUMMARY.txt` (шаг → ok/fail/skipped), `env.txt`,
`nvidia-smi-q.txt`, `ptxas_kernels.txt` (регистры и spill'ы kernel'ов), `cupqc_report.txt` (режим context string
ML-DSA, подтверждение/опровержение предположений об entropy), `gpu_clocks_before/after.txt`, `results_*.csv/json`,
`analysis/` (summary.md, speedup.csv, crossover.csv, transfer_bw.csv, plots/).

## Чек-лист объяснения границ (часть В)

Для каждой границы указать, какой фактор её определяет, со ссылкой на данные:

- **Накладные расходы запуска kernel'а** — точки с малым числом объектов/batch: доля `kernel` в разбивке фаз мала.
- **Передача по PCIe** — сравнить `h2d_gbps` (`transfer_bw.csv`) с паспортной шириной слота; для sha3 с малым размером
  объекта выигрыш невозможен, пока `bytes / h2d_gbps` больше времени CPU.
- **Аллокации** — серия `gpu_alloc_in_total.json`: разница `gpu-alloc-per-call` и `gpu-pooled`; для cuPQC workspace и
  entropy всегда выделяются библиотекой (пулирование их не убирает).
- **Последовательность sponge** — серия `gpu_hash_strategy.json` (поток на объект против warp на объект); один крупный
  объект (16 MiB × 10) ожидаемо проигрывает.
- **Divergence в ML-DSA sign** (rejection sampling) — масштабирование `mldsa_sign` по batch слабее, чем у keygen/verify.
- **Объём VRAM** — точки с порционированием (`gpu_double_buffering.json`), поведение при больших batch.
- **Entropy** — `entropy_ms` в разбивке PQC-операций.

**Правило интерпретации пересечений.** `crossover.csv` считает выигрыш строго по `speedup > 1`. В зоне, где GPU и CPU почти равны, шум измерений переворачивает знак, и получаются исходы `mixed` или «пересечение», которого нет. Прежде чем писать границу в таблицу, сверить её с разбросом между прогонами (`spread` в `summary.md`): если `|speedup − 1|` в соседних точках меньше разброса, это **ничья**, а не граница. При одном полном прогоне разброса нет, и такие точки помечаются как неуверенные.

## Практическая рекомендация для vault (часть В)

Какой backend выбирать в `vault verify` при каком размере хранилища: _по данным: пересечение для sha3/merkle_build
по числу и размеру объектов_. Для одиночных PQC-операций (одна подпись/Decaps на команду) GPU на batch = 1 ожидаемо
проигрывает: смысл GPU — серверный сценарий (много хранилищ, пакетная проверка).

## Ограничения эксперимента

- одна модель GPU (RTX 3050, SM 86) и одна модель CPU; результаты не переносятся на другие пары без повторных замеров;
- число полных прогонов (стабильность оценивается по ним; одиночный прогон стабильность не показывает);
- TrustedState — локальный файл (модель доверенной области, не TPM/HSM); power-loss тестирование не проводилось;
- cuPQC используется как есть; режим context string и раскладка entropy определены прогоном (`cupqc_report.txt`);
- GPU total включает аллокации (§48); при `pool_buffers = true` результат другой — обе серии приведены отдельно;
- измерения требуют governor `performance` и отсутствия фоновой нагрузки (`env.txt`).

## Воспроизводимость стенда

Release: `-O3 -DNDEBUG` **без `-march=native`** (скрипт запуска помечает `fail`, если оно задано; CMake предупреждает);
флаги и версии (CPU, ОС, компилятор, CUDA runtime/драйвер, OpenSSL, liboqs, коммит с признаком `-dirty`, потоки cpu-mt)
записываются в `results.json` и в начало `summary.md`.
