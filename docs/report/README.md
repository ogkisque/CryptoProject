Все числа и графики ниже взяты из файлов, которые сгенерировал `bench/analysis/analyze.py` (`results/*/summary.md`, `crossover.csv`, `speedup.csv`); руками числа не правились. ## Вопрос исследования (§44)

При каких размерах объектов, числе независимых операций и размере batch GPU даёт выигрыш над CPU с учётом передачи данных, аллокаций, синхронизации и запуска kernel'ов?

**Отклонение от ТЗ:** ТЗ называет RTX 3050 (SM 8.6); измерения сделаны на RTX 4060 (SM 8.9) — та же архитектурная линейка Ampere/Ada с 8 ГБ, но другая карта. Абсолютные числа на RTX 3050 будут ниже, качественные выводы (что доминирует и почему) переносятся.

**Стабильность:** 209 точек измерены в обоих прогонах; медиана разброса между прогонами **0.8 %**, 90-й процентиль 5 %, разброс > 10 % — у 10 точек (5 %), в основном малые задачи `cpu-mt` и `mldsa_keygen` gpu при batch 10000 (24 %). Границы ниже по смыслу не меняются от прогона к прогону (сравнение с предварительными запусками — в журналах этапов 5–6).

## Главный результат

1. **Вычисления на GPU быстрые, накладные расходы — нет.** Чистый kernel SHA3 даёт ≈ 51–53 GB/s на множестве мелких объектов (1 KiB × 100 000 за 1.9 мс) — в ~20–25 раз быстрее 12 потоков CPU (2–3 GB/s). Но в честном total (§48) 75–95 % времени GPU — **аллокация pinned- и device-памяти на каждый вызов и передача по PCIe** (`results/main/plots/gpu_phases_sha3.png`).
2. **Поэтому в режиме по умолчанию GPU обгоняет однопоточный CPU, но не 12 потоков:** SHA3 и Merkle build быстрее `cpu` с ≈ 100–2 000 объектов, а против `cpu-mt` пересечения нет нигде (максимум 0.37× для SHA3, 0.55× для Merkle build).
3. **Если убрать аллокации (пул буферов) и перекрыть копирование с вычислением (double buffering), GPU обгоняет и `cpu-mt`:** SHA3 до 1.5× (пул), до **1.77×** (пул + double buffering, 4 KiB × 50 000).
4. **Там, где передаётся мало данных на много вычислений, GPU выигрывает уверенно:** пакетная проверка Merkle-proof'ов — до **11.2×** против `cpu-mt`; ML-KEM/ML-DSA — до **1.5–2.3×** против `cpu-mt` при batch от нескольких сотен.
5. **Одиночные операции и один большой объект — всегда CPU:** на batch = 1 GPU в 12–60 раз медленнее `cpu-mt`; объект 16 MiB хешируется на GPU в ~15 раз медленнее `cpu-mt` (sponge последователен внутри сообщения).

## Объяснение границ (по данным)

- **Аллокации.** Серия `gpu_alloc_in_total`: при аллокации на каждый вызов SHA3 1 MiB × 1000 — 1 276 мс, из них ~905 мс `alloc`; с пулом — 373 мс. Против однопоточного `cpu` пул сдвигает порог с ≈ 270 до ≈ 60 объектов. Для cuPQC пул не помогает полностью: workspace и entropy библиотека выделяет сама на каждый вызов.
- **PCIe и сборка данных.** Эффективная H2D ≈ 3.6 GB/s (медиана; максимум 5.4 GB/s) при паспортных ~13 GB/s PCIe 4.0 x8. Узкое место — однопоточная сборка разрозненных объектов в pinned staging-буфер на CPU; pinned и pageable память почти не различаются (`gpu_pinned_vs_pageable`: pinned быстрее на 2–12 %). Double buffering прячет это за вычислением и даёт первый честный выигрыш у `cpu-mt`.
- **Последовательность sponge.** SHA3 одного сообщения не параллелится: на 16 MiB × 10 kernel занимает ~940 мс — каждый из 10 потоков хеширует свои 16 MiB со скоростью ~18 MB/s, суммарно ≈ 0.17 GB/s. Стратегия «warp на объект» (25 lane'ов на состояние) помогает при немногих крупных объектах (1 MiB × 100: 70 мс против 110 мс у «потока на объект»; `cpu-mt` — 36 мс), но проигрывает при многих мелких (`gpu_hash_strategy`); ни одна стратегия не догоняет 12 потоков CPU на крупных объектах.
- **Запуск kernel'а и синхронизация.** Фиксированная цена ~0.5–1 мс на вызов: при batch = 1 GPU в 12–60 раз медленнее `cpu-mt`; для PQC окупается с batch порядка сотен–тысяч (тем раньше, чем тяжелее операция: ML-DSA раньше ML-KEM).
- **Divergence в ML-DSA sign.** Подпись использует rejection sampling; разное число итераций внутри одного запуска — sign масштабируется хуже verify (1.65× против 2.27× при batch 10 000).
- **Регистры.** У всех kernel'ов SHA3/Merkle 0 байт spill (`results/raw/ptxas_kernels.txt`): «поток на объект» — 122 регистра, warp — 60, уровни Merkle — 71, proof'ы — 80; ограничение регистров не является узким местом.
- **Entropy cuPQC** (`entropy_ms`) — часть фиксированной цены PQC-операций; сама генерация на GPU быстрая.

## Практическая рекомендация для vault

- **`vault verify` и любые одиночные операции — CPU (`cpu-mt`).** Хранилище из тысяч файлов проверяется на 12 потоках быстрее, чем на GPU с аллокациями на каждый вызов; одна подпись Manifest или один Decaps на команду — всегда CPU.
- **GPU оправдан в серверном сценарии**: долгоживущий процесс с пулом буферов и double buffering, проверяющий много хранилищ или большое хранилище из десятков тысяч мелких объектов (SHA3/Merkle до 1.5–1.8× против 12 потоков), пакетная проверка Merkle-proof'ов (до 11×), пакетные ML-KEM/ML-DSA от нескольких сотен операций (1.5–2.3×).
- **Подпись Manifest — только CPU**: cuPQC SDK 0.6.0 подписывает ML-DSA только с пустым context string (см. ниже), а vault требует контекст `edu-vault-manifest-v1`.

## Совместимость cuPQC (проверено на устройстве)

| Свойство | Результат |
|---|---|
| ML-KEM-768 и ML-DSA-65 совместимы с liboqs (FIPS 203/204) в обе стороны | да (перекрёстные тесты, кросс-открытие хранилищ gpu↔cpu) |
| Entropy ML-KEM = FIPS 203 `d‖z` / `m` | да: 16/16 ACVP-векторов байт-в-байт |
| Entropy ML-DSA keygen = FIPS 204 `ξ` | да: 8/8 ACVP-пар ключей байт-в-байт |
| Entropy ML-DSA sign = FIPS 204 `rnd` | да: 1/1 ACVP-подпись байт-в-байт (единственный вектор выборки с пустым ctx) |
| Context string ML-DSA | **не поддерживается**: cuPQC выполняет pure-обёртку FIPS 204 с пустым ctx (калибровка `PureEmptyContext`). Batch с контекстом честно отказывает, одиночные операции vault с контекстом идут на CPU |

## Ограничения эксперимента

- одна модель GPU (RTX 4060, не RTX 3050 из ТЗ) и одна модель CPU; результаты не переносятся на другие пары без повторных замеров;
- 2 полных прогона (стабильность оценена по ним), одна сессия на одной машине; governor CPU не переключался в `performance`;
- ML-DSA sign/verify на GPU измерены только с пустым context string (ограничение cuPQC); в основной матрице с контекстом Manifest эти GPU-точки пропущены;
- TrustedState — локальный файл (модель доверенной области, не TPM/HSM); crash-тесты — на уровне процесса, power-loss не моделировался;
- cuPQC используется как есть (версия 0.6.0); сборка H2D однопоточная — многопоточная сборка staging или `cudaHostRegister` исходных буферов могли бы поднять ширину H2D, это не исследовалось;
- total GPU по умолчанию включает аллокации (§48); при `pool_buffers = true` результаты другие — обе серии приведены отдельно.
