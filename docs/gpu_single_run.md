# Модель работы: один запуск на GPU

**Решение (2026-10-16):** весь код этапов 5–7 пишется и максимально проверяется на машине разработки без GPU. Сюда входят GPU-backend'ы, benchmark, анализ результатов и генерация отчётных таблиц и графиков. На GPU-машину приходим **один раз** с готовым репозиторием, запускаем **один скрипт** и уносим **один архив** с результатами. Второго захода не планируется.

Отсюда требования:
1. Всё, что можно проверить без GPU, проверяется до запуска (уровни ниже).
2. Всё, что может сломаться только на GPU, имеет **запасной путь внутри скрипта**: сбой одной части не должен лишить нас остальных данных.
3. Скрипт пишет всё, что может понадобиться потом, в том числе то, что сейчас кажется лишним. Переснять данные будет негде.

## Что проверяется без GPU (до запуска)

| Уровень | Как | Что ловит |
|---|---|---|
| 1. Компиляция и линковка CUDA-кода | На этой машине ставится **CUDA Toolkit** (nvcc работает без GPU) и скачивается **cuPQC SDK** (заголовки и статические библиотеки). Сборка `-DVAULT_ENABLE_CUDA=ON` должна проходить здесь. GPU-тесты делают `GTEST_SKIP`, если устройства нет | синтаксис, сигнатуры cuPQC, CMake/RDC/LTO, ошибки линковки — большую часть «вслепую написанного» кода |
| 2. Логика kernel'ов | Keccak-f[1600], sponge SHA3-256 с domain-префиксом, шаг уровня Merkle и проверка proof пишутся как `__host__ __device__` функции в `cuda/kernels/*.cuh` (макрос `VAULT_HD`, без nvcc он пустой). Их компилирует g++, и **на CPU они тестируются против OpenSSL и reference** | ошибки алгоритма: границы rate (135/136/137 байт), префикс, непарный узел |
| 3. Host-часть GPU backend'ов | Упаковка `PackedBatch`, порционирование по объёму VRAM, расчёт grid/block, разбиение уровней Merkle — обычный C++ без CUDA API (`cuda/host/`), с юнит-тестами на CPU | ошибки индексов, переполнения, неверные чанки |
| 4. API cuPQC | Изучается по документации и заголовкам SDK здесь. Ответы на вопросы `06_gpu_pqc.md` §6.0 фиксируются **до** запуска, сигнатуры проверяет уровень 1 | неверные предположения о seed/entropy/context |
| 5. Benchmark | Полная матрица прогоняется на `cpu` и `cpu-mt` здесь (время и память замерены, см. ниже). Самопроверка результатов (§42) встроена в benchmark: неверный результат backend'а роняет точку, а не даёт «быстрый» замер | падения, нехватка памяти, неверная оценка времени |
| 6. Анализ и отчёт | `bench/analysis/analyze.py` разрабатывается на реальных CPU-данных и на **синтетическом CSV с gpu-строками** (тест анализа). Графики, crossover и `summary.md` создаются без ручных правок | анализ «не готов» к виду реальных GPU-данных |
| 7. Сценарий запуска | `scripts/gpu_run_all.sh` прогоняется здесь до конца (GPU-шаги дают «skipped») и собирает архив | ошибки в самом скрипте, отсутствующие файлы, неверные пути |

## Единственный запуск: `scripts/gpu_run_all.sh`

Каждый шаг пишет лог в отдельный файл. **Сбой шага не останавливает следующие**, кроме полной невозможности собрать проект. В конце всегда собирается архив.

| Шаг | Действие | Запасной путь при сбое |
|---|---|---|
| 0 | Снимок окружения: `check_gpu_env.sh`, `nvidia-smi -q`, `lscpu`, `free`, `df`, governor, `git describe --dirty`, версии CUDA и cuPQC | — |
| 1 | Release-сборка `VAULT_ENABLE_CUDA=ON` + cuPQC | → сборка без cuPQC (GPU только SHA3/Merkle) → CPU-only сборка (хотя бы CPU-данные на этой же машине для честного сравнения) |
| 2 | `ctest` полностью, включая метку `gpu` (эквивалентность CPU==GPU, ACVP на GPU) с JUnit XML | backend, не прошедший эквивалентность, исключается из benchmark'а (его данные недостоверны), остальные идут дальше |
| 3 | Smoke vault: `init/add/verify/extract --backend gpu`, кросс-открытие хранилищ cpu↔gpu | записать и продолжить |
| 4 | `bench/configs/quick.json` (минуты) — проверка, что GPU-путь вообще работает | при падении — full только для cpu/cpu-mt |
| 5 | `bench/configs/full.json`, затем 2-й (и 3-й, если позволяет бюджет) повтор для оценки стабильности медиан | каждая точка с самопроверкой; упавшая точка → запись с причиной, прогон продолжается |
| 6 | Дополнительные серии: pinned/pageable, `include_alloc_in_total` on/off, пул буферов, double buffering SHA3 — `bench/configs/gpu_*.json` | — |
| 7 | `analyze.py` по всем CSV → `summary.md`, графики, `crossover.csv` | сырые CSV всё равно в архиве: анализ можно повторить дома |
| 8 | Архив `bench/results/<ts>_<host>.tar.gz`: логи, CSV/JSON, ctest XML, окружение, графики | — |

Параметр `--time-budget <минуты>` ограничивает шаги 5–6: повторы и дополнительные серии запускаются, только пока бюджет не исчерпан. Обязательная часть (шаги 0–5, один проход full) должна укладываться в оценку ниже.

## Оценка времени и памяти

**Замер на машине разработки (2026-10-16, 12 потоков):** полная матрица `full.json` для `cpu` и `cpu-mt` — **10 мин 34 с** wall-clock (вместе с генерацией входов и самопроверкой результатов), пиковая RSS — **1.6 GiB**. 24 комбинации пропущены по `max_total_bytes` (в основном 100000 × 64 KiB и выше). Самые долгие серии: `sha3` и `merkle_build` на `cpu` (~2 мин каждая), `mldsa_sign` на `cpu` (~1.5 мин).

Оценка для GPU-машины: CPU там может быть в 1.5–2 раза медленнее, GPU-точки добавляют время порядка `cpu-mt` плюс инициализацию CUDA-контекста. **Обязательная часть (сборка ≈ 5 мин, ctest, quick, один проход full) ≈ 30–40 мин**; каждый повтор full — ещё ≈ 20–25 мин. Разумный `--time-budget`: 90–120 мин.

Память: самая большая точка — 16 MiB × 100 = 1.6 GiB данных. На хосте хватит **≥ 4 GiB свободной RAM**, VRAM — с порционированием по `max_chunk_bytes`. Скрипт всё равно проверяет `free` и `cudaMemGetInfo`.

## Подготовка GPU-машины (не требует нашего кода)

- Драйвер NVIDIA, **CUDA Toolkit той же major.minor**, что использовалась для компиляции здесь, и **cuPQC SDK той же версии**.
- cmake ≥ 3.22, gcc, поддерживаемый этим nvcc, `libssl-dev`, Python 3 с pandas и matplotlib.
- Зависимости FetchContent (liboqs, CLI11, GoogleTest, nlohmann/json) берутся из **заранее подготовленного архива** (`scripts/vendor_deps.sh` → `third_party/*.tar.gz`, сборка с `FETCHCONTENT_FULLY_DISCONNECTED=ON`), чтобы не зависеть от сети на GPU-машине.

## Готовность к запуску (gate)

Запуск разрешён, только когда отмечены все пункты:

- [ ] Этапы 5, 6, 7 закрыты по своим «частям А».
- [ ] `-DVAULT_ENABLE_CUDA=ON` с cuPQC собирается и линкуется на этой машине, без предупреждений.
- [ ] Тесты host-функций kernel'ов (`VAULT_HD`) и host-части GPU-backend'ов проходят на CPU.
- [ ] Ответы на вопросы cuPQC (§6.0 этапа 6) записаны, обёртки соответствуют документации SDK.
- [ ] `analyze.py` проходит свои тесты на CPU-данных и синтетических GPU-данных; `summary.md` и графики создаются.
- [ ] `scripts/gpu_run_all.sh` доходит до конца на этой машине и собирает архив (GPU-шаги — skipped).
- [ ] Зависимости завендорены, офлайн-сборка проверена (`FETCHCONTENT_FULLY_DISCONNECTED=ON`).
- [ ] Версии CUDA и cuPQC для GPU-машины записаны.
- [ ] Время обязательной части оценено и укладывается в доступное окно.

## Риски

| Риск | Что делаем |
|---|---|
| На GPU-машине другая версия CUDA или драйвер не поддерживает toolkit | версии фиксируются заранее (gate); шаг 1 падает в CPU-only сборку, CPU-данные с той же машины всё равно собираются |
| cuPQC ведёт себя иначе, чем по документации (seed, context) | GPU ML-KEM/ML-DSA проходят эквивалентность в шаге 2; при провале исключаются из benchmark, SHA3/Merkle-данные сохраняются |
| Нехватка VRAM (у RTX 3050 4/6/8 GiB) | порционирование по `max_chunk_bytes`, которое скрипт выставляет по `cudaMemGetInfo`, протестировано на CPU (уровень 3) |
| Дрейф частот и нагрев | снимок `nvidia-smi` до и после каждого прогона full; повторы full для оценки стабильности |
| Не хватило времени | бюджет `--time-budget`; обязательная часть (≈ 30–40 мин) отделена от дополнительной |
