# Этап 7: экспериментальное исследование и сценарий запуска на GPU

**Статус:** ☐ не начат  ·  **Где:** часть А — на этой машине, часть Б — запуски на GPU-машине (автор), часть В — анализ присланных данных  ·  **ТЗ:** план → Этап 7, `crypto_project.md` §44–§49, §56

## Цель

Ответить на исследовательский вопрос (§44): при каких размерах объектов, количестве операций и размере batch GPU даёт выигрыш над CPU с учётом передачи данных, аллокаций, синхронизации и запуска kernel'ов. GPU-код собирается и запускается автором на GPU-машине (`docs/gpu_workflow.md`), поэтому здесь заранее готовятся сценарий запуска и анализ: присланный архив должен сразу превращаться в таблицы и графики.

## Часть А — на этой машине

### 7.A1 Анализ (`analyze.py`)
- [ ] Загрузка CSV из `vault benchmark` (столбцы — `write_csv`); пропуск `skipped`, учёт записей с ошибкой самопроверки.
- [ ] speedup = CPU_total / GPU_total (медианы) против **cpu и против cpu-mt**.
- [ ] crossover point для каждого класса операций: SHA3 (по количеству при фиксированном размере и по размеру при фиксированном количестве), Merkle build, Merkle verify (по числу листьев), каждая из шести PQC-операций (по batch). Интерполяция в log-шкале; «нет пересечения в диапазоне» — отдельный явный результат.
- [ ] Графики: throughput (GB/s) от размера; ops/s от batch; stacked bar фаз GPU (alloc/H2D/kernel/D2H/sync); heatmap speedup (size × count) для SHA3.
- [ ] Несколько прогонов full → стабильность медиан (разброс между прогонами) в `summary.md`.
- [ ] `summary.md` и графики — только из скрипта, без ручной правки чисел.
- [ ] `test_analyze.py`: фикстура из реального CPU-прогона здесь и **синтетический CSV с gpu-строками**, включая GPU быстрее, медленнее, пересечение внутри и вне диапазона, skipped-точки и упавший backend. Анализ не должен падать ни на одном варианте.

### 7.A2 Сценарий запуска (`gpu_run_all.sh`)
- [ ] Шаги из `docs/gpu_workflow.md`: окружение → сборка (без cuPQC, если он не найден) → `ctest` → smoke vault → `quick.json` → *(без `--quick`)* `full.json` и `gpu_*.json` → `analyze.py` → архив.
- [ ] Лог каждого шага в отдельном файле, итог «шаг → ok/fail/skipped» в `RUN_SUMMARY.txt`; сбой шага не останавливает следующие.
- [ ] `nvidia-smi --query-gpu=clocks.sm,temperature.gpu,power.draw` до и после прогона full.
- [ ] Архив собирается всегда, даже после сбоев (`trap EXIT`).
- [ ] Прогон здесь в CPU-режиме: скрипт доходит до конца, GPU-шаги — skipped, архив собран и проходит через `analyze.py`.

### 7.A3 Стенд
- [ ] Флаги Release зафиксированы и записаны. Для воспроизводимости — **без** `-march=native` или с явным `-march=<target>`.
- [x] CPU-часть full замерена (10.5 мин, 1.6 GiB, ревью этапа 4) и вписана в `docs/gpu_workflow.md`.

## Часть Б — на GPU-машине (автор)

1. `CUPQC_ROOT=... ./scripts/gpu_run_all.sh --quick` → прислать `RUN_SUMMARY.txt` и архив (или `build.log`, если не собралось). Повторять после исправлений, пока быстрый прогон не станет зелёным.
2. `./scripts/gpu_run_all.sh` (полный; желательно 2–3 раза для оценки стабильности медиан) → прислать архивы.
