# Этап 7: экспериментальное исследование и сценарий единственного запуска

**Статус:** ☐ не начат  ·  **Где:** часть А — на этой машине (без GPU), часть Б — единственный запуск, часть В — анализ дома  ·  **ТЗ:** план → Этап 7, `crypto_project.md` §44–§49, §56

## Цель

Ответить на исследовательский вопрос (§44): при каких размерах объектов, количестве операций и размере batch GPU даёт выигрыш над CPU с учётом передачи данных, аллокаций, синхронизации и запуска kernel'ов. Поскольку на GPU мы выходим один раз (`docs/gpu_single_run.md`), основная работа этапа — **сделать так, чтобы этот запуск гарантированно дал полные и пригодные для анализа данные**.

## Часть А — на этой машине (до запуска)

### 7.A1 Анализ (`analyze.py`) — полностью готов до запуска
- [ ] Загрузка CSV из `vault benchmark` (столбцы — `write_csv`); пропуск `skipped`, учёт записей с ошибкой самопроверки.
- [ ] speedup = CPU_total / GPU_total (медианы) против **cpu и против cpu-mt**.
- [ ] crossover point для каждого класса операций: SHA3 (по количеству при фиксированном размере и по размеру при фиксированном количестве), Merkle build, Merkle verify (по числу листьев), каждая из шести PQC-операций (по batch). Интерполяция в log-шкале; «нет пересечения в диапазоне» — отдельный явный результат.
- [ ] Графики: throughput (GB/s) от размера; ops/s от batch; stacked bar фаз GPU (alloc/H2D/kernel/D2H/sync); heatmap speedup (size × count) для SHA3.
- [ ] Несколько прогонов full → стабильность медиан (разброс между прогонами) в `summary.md`.
- [ ] `summary.md` и графики — только из скрипта, без ручной правки чисел.
- [ ] `test_analyze.py`: фикстура из реального CPU-прогона здесь и **синтетический CSV с gpu-строками**, включая GPU быстрее, медленнее, пересечение внутри и вне диапазона, skipped-точки и упавший backend. Анализ не должен падать ни на одном варианте.

### 7.A2 Сценарий запуска (`gpu_run_all.sh`)
- [ ] Шаги 0–8 и запасные пути из `docs/gpu_single_run.md`. Лог каждого шага в отдельном файле, итоговая таблица «шаг → ok/fail/skipped» в `RUN_SUMMARY.txt`.
- [ ] `--time-budget`: обязательная часть (0–5, один проход full) всегда; повторы full и `gpu_*.json` — пока есть время.
- [ ] Проверка ресурсов перед benchmark'ом: `free` против `max_total_bytes`, `cudaMemGetInfo`. При нехватке — уменьшенная копия конфига, с записью в лог.
- [ ] `nvidia-smi --query-gpu=clocks.sm,temperature.gpu,power.draw` до и после каждого прогона full.
- [ ] Архив всегда собирается в конце, даже после сбоев (`trap EXIT`).
- [ ] **Прогон здесь:** скрипт доходит до конца, GPU-шаги — skipped, архив собран и проходит через `analyze.py`.

### 7.A3 Офлайн-сборка и стенд
- [ ] `scripts/vendor_deps.sh` → `third_party/*.tar.gz`; сборка с `FETCHCONTENT_FULLY_DISCONNECTED=ON` проверена здесь.
- [ ] Флаги Release зафиксированы и записаны. Для воспроизводимости — **без** `-march=native` или с явным `-march=<target>`.
- [x] CPU-часть full замерена (10.5 мин, 1.6 GiB, ревью этапа 4) и вписана в `docs/gpu_single_run.md`.
- [ ] Уточнить оценку после появления GPU-кода (прогон `gpu_run_all.sh` здесь).

## Часть Б — единственный запуск

`./scripts/gpu_run_all.sh --time-budget <мин>` и унести архив `bench/results/<ts>_<host>.tar.gz`. Руками ничего не делать, кроме чтения `RUN_SUMMARY.txt` перед уходом. Если там fail на шаге 1 или 2, логи всё равно в архиве.

## Часть В — анализ дома

- [ ] Распаковать архив, прогнать `analyze.py` (повторно, если что-то донастроено, — сырые данные в архиве).
- [ ] Таблица «CPU предпочтителен / GPU предпочтителен» по классам операций и диапазонам.
- [ ] Объяснение каждой границы: launch overhead, PCIe-трансфер (по H2D GB/s из разбивки фаз), последовательность sponge, divergence в ML-DSA sign, объём VRAM.
- [ ] Практическая рекомендация для vault: какой backend выбирать в `verify` при каком размере хранилища.
- [ ] Ограничения эксперимента: одна модель GPU, **один запуск** (оценка стабильности только по повторам внутри него), модель доверенной области, отсутствие power-loss тестов.
- [ ] Выводы в `docs/report/`.
