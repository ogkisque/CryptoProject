# Этап 6: GPU-backend для ML-KEM-768 и ML-DSA-65

**Статус:** ☐ не начат  ·  **Где:** часть А — на этой машине (без CUDA, код не компилируется), часть Б — сборка и запуск на GPU-машине автором (`docs/gpu_workflow.md`)  ·  **ТЗ:** план → Этап 6, `crypto_project.md` §42–§43, §46–§47

## Цель

Реализовать `IKemBackend` и `ISigBackend` на cuPQC, проверить совместимость с CPU (liboqs) и найти минимальный batch, с которого GPU выгоднее. Своих реализаций ML-KEM/ML-DSA нет: работает cuPQC, поэтому самый большой риск — **неверные предположения о его API**. SDK здесь нет, поэтому API берётся из публичной документации NVIDIA, а все неочевидные места явно помечаются `// UNVERIFIED(cuPQC): ...`. При ошибке на GPU-машине сразу видно, какое предположение не подтвердилось.

## Часть А — на этой машине (до запуска)

### 6.A0 Разведка API cuPQC по публичной документации (до кода)
Ответить и записать ответы в журнал этого файла **со ссылкой на место в документации**. То, что из документации не ясно, записать как предположение, а в коде пометить `UNVERIFIED`:
- [ ] Версия SDK. Есть ли ML-KEM-768 и ML-DSA-65.
- [ ] Модель вызова: device-side API (свой `__global__` вызывает `cupqc::...` с workspace и shared memory) или host API. Сколько shared memory и потоков нужно на операцию, сколько операций помещается в блок.
- [ ] **Источник случайности:** принимает ли cuPQC entropy/seed от вызывающего? Если да — keygen/encaps сравниваются с liboqs **байт-в-байт** на одних seed (тест сильнее, чем требует §42). Если нет — только взаимная проверка.
- [ ] **Context string ML-DSA.** Если `ctx` не поддерживается — собирать `M' = 0x00 || len(ctx) || ctx || M` вручную и вызывать «internal» sign/verify, если он есть. Если нет ни того, ни другого — GPU ML-DSA только в benchmark'е с пустым ctx, а в vault используется CPU. Обязательно оговорить в отчёте.
- [ ] Детерминированная подпись (rnd = 0^32) — есть ли.
- [ ] Требования к сборке: RDC, LTO, флаги, порядок линковки → `cmake/Cuda.cmake`.

### 6.A1 Host-часть
- [ ] `pqc_batch_plan`: разбиение batch'а на порции по VRAM, `blockDim`/shared memory по ответам 6.A0. Тесты на граничные batch (1, 10000, не кратные размеру блока).
- [ ] Entropy генерируется на CPU (`RAND_bytes`) и копируется H2D. Решить и записать, входит ли её генерация в total (рекомендация: не входит, но измеряется отдельно).

### 6.A2 Device-код (вслепую, здесь не компилируется)
- [ ] `gpu_kem_backend.cu`: `keygen_batch`, `encaps_batch`, `decaps_batch` на плоских буферах `KemBatch` (`docs/format_v1.md` §15). Одиночные операции = batch из 1.
- [ ] `gpu_sig_backend.cu`: `keygen_batch`, `sign_batch`, `verify_batch` на `SigBatch` (сообщения по 168 байт, как Manifest).
- [ ] **Секреты на GPU (§43):** после операции — `cudaMemsetAsync(0)` для `secret_keys`, `shared_secrets` и workspace, затем освобождение (или возврат в пул уже обнулённым).
- [ ] Тайминг по фазам, как в этапе 5; ошибки через `CUDA_CHECK`. Коды возврата cuPQC (если есть) проверяются и попадают в текст ошибки.
- [ ] Если cuPQC не найден при сборке, KEM/DSA GPU-backend'ы дают `BackendUnavailable`, а SHA3/Merkle на GPU работают (`VAULT_HAS_CUPQC`).

### 6.A3 Тесты для запуска
- [ ] `tests/gpu/gpu_pqc_test.cpp`:
  - ACVP-векторы на GPU (keyGen и encapDecap ML-KEM; keyGen, sigGen и sigVer ML-DSA) — те же файлы, что для CPU (`tests/vectors/`);
  - перекрёстные проверки: GPU encaps → CPU decaps и наоборот; GPU sign → CPU verify и наоборот; испорченная подпись невалидна на обоих;
  - при seed-API: keygen, encaps и детерминированный sign совпадают с CPU байт-в-байт;
  - vault: хранилище, созданное с `--backend gpu`, открывается на CPU, и наоборот.
  - Без устройства — `GTEST_SKIP`.
- [ ] Benchmark уже проверяет результаты GPU через reference (ревью этапа 4): ключи работают, decaps reference = секреты backend'а, подписи проходят reference verify.

## Часть Б — на GPU-машине (собирает и запускает автор)

- `gpu_run_all.sh --quick`: сборка с cuPQC, `ctest -L gpu` (ACVP, перекрёстные проверки). Ошибки присылаются; по ним пересматриваются помеченные `UNVERIFIED` места, итерация повторяется.
- Когда быстрый прогон зелёный — полный: матрица PQC из `full.json`, batch {1, 10, 100, 1000, 10000} × 6 операций × {cpu, cpu-mt, gpu}.
- В журнал: какие предположения 6.A0 подтвердились, какие нет и что изменено.

## Тонкие места

* В vault на одну операцию приходится ровно одна PQC-операция (1 sign или 1 decaps). На batch = 1 GPU почти наверняка проиграет, это нормально. Смысл GPU для PQC здесь — серверный сценарий: много хранилищ или пользователей, пакетная проверка. Так и сформулировать в отчёте.
* Время ML-DSA sign недетерминировано (rejection sampling): divergence в warp'е — возможная причина плохого масштабирования.
