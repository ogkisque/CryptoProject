# Этап 6: GPU-backend для ML-KEM-768 и ML-DSA-65

**Статус:** ☐ не начат  ·  **Где:** часть А — на этой машине (без GPU), часть Б — автоматически в единственном запуске (`docs/gpu_single_run.md`)  ·  **ТЗ:** план → Этап 6, `crypto_project.md` §42–§43, §46–§47

## Цель

Реализовать `IKemBackend` и `ISigBackend` на cuPQC, проверить совместимость с CPU (liboqs) и найти минимальный batch, с которого GPU выгоднее. Своих реализаций ML-KEM/ML-DSA нет: работает cuPQC, поэтому самый большой риск — **неверные предположения о его API**. Их нужно снять до запуска по документации и заголовкам SDK.

## Часть А — на этой машине (до запуска)

### 6.A0 Разведка API cuPQC по документации и заголовкам SDK (до кода)
Ответить и записать ответы в журнал этого файла **со ссылкой на место в документации или заголовке**:
- [ ] Версия SDK. Есть ли ML-KEM-768 и ML-DSA-65.
- [ ] Модель вызова: device-side API (свой `__global__` вызывает `cupqc::...` с workspace и shared memory) или host API. Сколько shared memory и потоков нужно на операцию, сколько операций помещается в блок.
- [ ] **Источник случайности:** принимает ли cuPQC entropy/seed от вызывающего? Если да — keygen/encaps сравниваются с liboqs **байт-в-байт** на одних seed (тест сильнее, чем требует §42). Если нет — только взаимная проверка.
- [ ] **Context string ML-DSA.** Если `ctx` не поддерживается — собирать `M' = 0x00 || len(ctx) || ctx || M` вручную и вызывать «internal» sign/verify, если он есть. Если нет ни того, ни другого — GPU ML-DSA только в benchmark'е с пустым ctx, а в vault используется CPU. Обязательно оговорить в отчёте.
- [ ] Детерминированная подпись (rnd = 0^32) — есть ли.
- [ ] Требования к сборке: RDC, LTO, флаги, порядок линковки. Результат — пункт 6.A2 собирается здесь.

## Часть Б — в единственном запуске (делает скрипт)

- `ctest -L gpu` → при провале эквивалентности GPU-KEM/DSA исключаются из benchmark'а, SHA3/Merkle продолжаются.
- Матрица PQC из `full.json`: batch {1, 10, 100, 1000, 10000} × 6 операций × {cpu, cpu-mt, gpu}.
- В архив: фактическое поведение cuPQC (лог тестов), если оно разошлось с ответами 6.A0.

## Тонкие места

* В vault на одну операцию приходится ровно одна PQC-операция (1 sign или 1 decaps). На batch = 1 GPU почти наверняка проиграет, это нормально. Смысл GPU для PQC здесь — серверный сценарий: много хранилищ или пользователей, пакетная проверка. Так и сформулировать в отчёте.
* Время ML-DSA sign недетерминировано (rejection sampling): divergence в warp'е — возможная причина плохого масштабирования.
